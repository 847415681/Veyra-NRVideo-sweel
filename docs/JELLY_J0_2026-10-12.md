## 方法

- 程序：`tests/integration/FgMotionBoundaryTests.cpp` → `veyra_fg_motion_boundary_tests <输出目录> <dlss|fsr> <orbit|walk> <变体>`。
- 构建：`py -3.11 -I tmp/claude-jelly-20261012/build.py`。
  - 先逐个核对本工作树的产品源码与 Codex 合并构建回执（`logs/merge-current-fixes-20261011/build-20261011-221225`）一致；
  - 然后只编译这一个测试源文件，用该回执的测试链接文件链接。
- 运行：在私有 app 副本 `tests/claude-jelly-latency-20261012/app` 中运行，着色器、DLSS 310.9.1 和 FSR 3.1.6 运行库都取自其中。D3D12 调试层开启。
- 场景：4K 合成画面，按 30fps 内容的位移设计：每帧 40 px，A/B 原帧之间有精确的中间帧真值。
  - **orbit**：镜头转动，背景平移，人物在屏幕上静止；
  - **walk**：镜头不动，人物移动。
- 产品链路：
  - 光流在 1920×1080 上计算，与 4K 采集加实时 NR 相同；
  - 补帧 2X，不开 NR / SR；
  - 每组 10 张原帧，前 2 张作为预热，统计后 8 张生成帧。
- 补帧的运动输入用测试钩子 `fgMotionProbe` 替换：

| 变体 | 补帧收到的运动矢量 |
| --- | --- |
| zero | 全 0（只靠补帧自己的运动估计；XeSS 在“自动”下就是这样） |
| product | 产品光流：NVOF → NvofDensify → FlowAdapt |
| ideal | 逐像素精确矢量，露出区按背景运动给 |
| blocky | ideal 按 8×8 块中心取样（只模拟网格量化） |
| zeroband | ideal，但遮挡露出带和轮廓两侧各一块清零（只模拟清零） |
| inverted / garbage | 对照：ideal 取反 / 全屏 +120 px |
| nrflow / nrzero | 开 NR（1080p 实时），NR 运动分别取产品光流 / 0 |

- 指标：
  - 轮廓带：距人物轮廓 64 px 以内，统计生成帧与真值的 RGB 平均误差、单通道误差 >32 的像素比例和 P95；
  - 远处背景平均误差；
  - 抖动：只在 orbit 场景，统计静止人物内侧 64 px 以内相邻上屏帧的变化。
- 结果文件：`logs/claude-jelly-20261012/j0/j0-results.json`，每组日志、裁切图、误差图、`sheet-*.png` 在同一目录。

## 结果（RTX 5070）

### DLSS 补帧：完全不受运动矢量影响

| 变体 | orbit 轮廓带误差 / 坏点 | walk 轮廓带误差 / 坏点 |
| --- | --- | --- |
| zero | 2.774 / 2.59% | 2.579 / 2.29% |
| product | 2.773 / 2.59% | 2.580 / 2.29% |
| ideal | 2.774 / 2.59% | 2.579 / 2.29% |
| blocky / zeroband | 2.775 / 2.59% | 2.579 / 2.29% |
| inverted | 2.775 / 2.59% | 2.579 / 2.29% |
| garbage（全屏 +120 px） | 2.775 / 2.59% | 2.583 / 2.29% |

- 连明显错误的矢量都不改变结果，误差图也完全相同。
- 在产品现在的 DLSS-G 参数下（静止合成相机、常数深度、`cameraMotionIncluded=1`），DLSS 补帧基本只用自己的运动估计。
- 加上 `SR_FG_DEPTH_RESPONSE_2026-09-08.md`（深度几乎无响应），对 DLSS 补帧来说，我们能给的矢量和深度都改变不了轮廓结果。用户反馈“开启光流也没用”，与此一致。

### FSR 补帧：强烈依赖运动矢量，产品光流已接近理想

| 变体 | orbit 轮廓带 / 坏点 / 远处背景 | walk 轮廓带 / 坏点 |
| --- | --- | --- |
| zero | 6.586 / 8.12% / **16.26** | 10.521 / 17.21% |
| product | **1.542 / 1.83% / 0.10** | **2.041 / 3.13%** |
| ideal | 1.711 / 3.74% / 0 | 2.050 / 3.52% |
| blocky | 1.917 / 4.12% / 0 | 2.099 / 3.64% |
| zeroband | 1.710 / 2.09% / 0 | 2.842 / 5.82% |
| garbage | 24.08 / 47.13% / 17.91 | 25.27 / 49.63% |

- **没有矢量时**，镜头转动下整片背景不跟着动，远处背景误差 16。
- **产品光流**与理想矢量相当，orbit 下甚至更好。因此在干净画面上，“光流精修”（方案 J1）没有可测收益。
- **顺带发现一个缺陷**：`EnhanceGraph::initNvof` 只在补帧后端是 DLSS 时才为补帧创建光流（`frameGenerationBackend==Dlss`）。只开 FSR 补帧时，“光流/自动”实际给的是 0，必须同时开 NR 或 SR 才有光流。第一次跑 product 组时 NVOF 执行 0 次，结果与 zero 完全相同，就是这个原因；测试里给 product 组打开了独立光流，与开 NR 的用户一致。
- XeSS 走送显端补帧，创建光流的条件不同；它在“自动”下按设计给 0（`motionUsesFlow`）。

### NR 的影响（DLSS 2X）

| 组 | orbit 真实帧轮廓带误差 | 生成帧轮廓带 / 坏点 | 静止人物轮廓内侧抖动 |
| --- | --- | --- | --- |
| 不开 NR | 0 | 2.77 / 2.59% | 0.241 |
| NR，运动=0 | 8.98 | 10.77 / 20.63% | 0.452 |
| NR，运动=产品光流 | 11.47 | 13.00 / 35.89% | 0.376 |

- walk 场景：NR 光流 12.34 / 35.75%，NR 零运动 11.23 / 28.88%。
- NR 会改变画面，所以“与真值的误差”里包含正常的增强效果。
- 用产品光流时，轮廓带偏离原图更多，但静止人物内侧的逐帧抖动没有增加（3 组都在 0.5 级以下）。合成画面里没有复现出由 NR 引起的轮廓晃动。

## 判定

1. DLSS 用户的果冻不是我们的光流造成的，也不能靠改光流来修：DLSS 补帧不读这些矢量。
2. 吃矢量的补帧（以 FSR 代表）在干净的合成画面上，产品光流已经与理想矢量相当。方案 J1（光流精修）在 J0 里没有收益，**不建议实施**。
3. 合成场景（刚体、无模糊、无压缩噪声、每帧 40 px）里，DLSS 和 FSR 的轮廓误差都只是一条窄边，**没能复现**用户看到的明显果冻。真正的诱因还在真实画面的特性里：位移更大、运动模糊、压缩噪声、人物肢体动画、背景视差，或者游戏自身的 TAA 拖影。这些需要真实素材才能确认。
4. XeSS 没有测：它在送显端由提供方自行生成和显示，处理图读不回生成帧。SDK 3.0.2 有 `XEFG_SWAPCHAIN_DEBUG_FEATURE_SHOW_ONLY_INTERPOLATION`，可以配合抓屏单独实施。

## 边界

- 只测了合成画面和本机 RTX 5070、DLSS 310.9.1、FSR 3.1.6。没有真实游戏画面，没有 XeSS，没有其他显卡。
- 首次重跑 dlss-*-zero 时裁切图文件已存在、保存失败，所以那两条记为 pass=false；指标与之后的有效重跑一致，后来已改为覆盖保存。FSR 首轮因为测试程序按错误状态上传矢量，触发了调试层报错，修正后整组重跑，报错为 0。
