# 极限低延迟（不撕裂）修复方案（Claude，2026-10-13）

用户要求：“已经有垂直同步按钮了还把自动弄得和垂直同步一样，弄回原来的那种，和游戏同款的，我们软件首要要求就是延迟压到最低，现在重新写修复方案，延迟必须要做到极限的低！但不要允许撕裂”。

分支 `claude/latency-min-20261013`（从 main 7571919 开出），存档标签 `checkpoint/pre-claude-latency-min-20261013`。产物统一在 `E:/项目/Veyra/{build,tests,logs,tmp,reports}/claude-latency-min-20261013`。不合并 main、不推送、不发布，除非用户另行授权；不改运行库/模型/驱动/用户配置；每个测试 ≤300 秒，构建 ≤900 秒。

## 1. 现状问题（证据见 reports/claude-latency-20261013）

1. 2.0.6（ef2069f）把“自动”从 `Present(0,0)`（新帧替换未显示的旧帧）改成 `Present(1,0)`（垂直同步）。输出帧率超过刷新率时帧会排队：60Hz PBP 下 4K NR+XeSS 2X 光学延迟 112ms（关效果 33ms）。
2. 原生路径“垂直同步时队列 1 帧”实际没生效：设置了最大延迟 1，但默认模式没人等待可等待对象。小程序实测排 7 帧；320Hz 实卡 DLSS 6X（360fps）送显→上屏 P50 从 4X 的 5.6ms 涨到 11.8ms。现有“低延迟队列”和“跟随显示器上限”都压不住。
3. XeSS 路径：N 卡上 XeLL 不做“补帧时限到半刷新并对齐 VSync”（Intel 文档写明仅 Intel 显卡）；XeSS 与 NR 共用 GPU 队列；“GPU 未完成不叠第二帧”的门对 XeSS 关闭；XeLL 周期错位（上一帧送显前就开始下一帧的 XeLL 睡眠）。
4. 输出超过刷新率时，补帧的帧要么排队加延迟，要么在显示端被替换掉白算。

## 2. 设计原则

1. **永不排队**：显示器显示不过来的帧，要么不生成，要么在显示前被更新的帧替换；交换链、Intel 送显层、GPU 队列、调度器任何一级都不积压。
2. **不撕裂**：只有用户显式选择“允许撕裂”才传 `DXGI_PRESENT_ALLOW_TEARING`。
3. **节流只在读帧之前**：需要等待时只在读采集帧之前等；读入之后处理和送显全程不再等待（GPU 按队列顺序执行）。
4. **补帧只付原理成本**：真帧只等 (倍数−1)/倍数 个源间隔加补帧计算，不再有其他等待。
5. **不受限时不变**：输出低于刷新率时（例如 320Hz 下 2X/4X）画面和节奏与现在一致。

## 4. 理论延迟与验收目标（4K60 NV12 源，RTX 5070，相对 HDMI 直连）

组成：采集卡约 15ms（硬件/USB，软件无法改变）+ Veyra 基础约 3ms + NR 约 7ms + 补帧计算 2–3ms（VFG 约 15ms）+ 补帧原理等待 (倍数−1)/倍数×源间隔（60fps 2X 8.3ms）+ 等刷新 0–1 个刷新（VRR 下约 0）。

| 场景 | 关效果 | 仅 NR | NR+2X |
|---|---|---|---|
| 320Hz 日常 | ≈20ms | ≈27ms | ≈37–42ms |
| 60Hz PBP，60fps 源 | 33ms（实测，相位决定） | ≈33–50ms | A1 后≈45–55ms；B2 后=仅 NR |
| 60Hz PBP，30fps 源 | ≈33ms | ≈33–50ms | ≈50–60ms |

60Hz 下处理时间会被刷新量化（同一处理可能落在原本要等的空档里，也可能错过一个刷新）。320Hz 行为推算，最终以用户光学测量为准。
